# Mountee — Mac App Store Compatibility Audit

**Audit date:** 2026-11-14

**Audit baseline:** the current `main` working tree. At final review, `HEAD` is `e5f1863` (`v0.3.0`, three commits ahead of `origin/main`); the rebrand files are committed, while `.github/workflows/release.yml`, `Mountee.xcodeproj/project.pbxproj`, `Mountee/MenuView.swift`, `Mountee/MounteeApp.swift`, and `scripts/make-installer.sh` remain modified. Findings reflect their current contents. The audit added only this report.

**Method:** source, project, scripts, documentation, tests, current Apple documentation, and public App Store/GitHub pages inspected. No application files, entitlements, signing assets, workflows, or provisioning profiles were changed. No build, tests, App Store profile creation, or hardware validation was run as part of this audit.

## 1. Executive summary

**Can Mountee be released on the Mac App Store?** **Likely in principle, but not established for this build.** Apple explicitly describes FSKit modules delivered as app extensions as compatible with Mac App Store distribution. A live Mac App Store listing also advertises an NTFS product using a sandboxed FSKit extension. Neither fact establishes that Mountee's host entitlement and its disk operations will work in a sandboxed App Store build.

**Is the current build compliant?** **No — Confirmed.** The main app has no `com.apple.security.app-sandbox` entitlement, is signed for Developer ID distribution, and uses private `fskitd` XPC selectors, writes Apple's internal FSKit enablement plist, and force-kills `fskit_agent`. Those paths conflict with Mac App Store sandbox and documented-API requirements. The existing release pipeline creates `MAC_APP_DIRECT` profiles and a notarized DMG, not an App Store archive.

**What blocks submission?** The host app must be sandboxed, and the App Store binary must not depend on the private enablement route or the `/sbin/mount` fallback. More importantly, the audit could not establish that the App Store provisioning profile for the current IDs will authorize `com.apple.developer.fskit.mount`, or that the current Disk Arbitration and `/dev` discovery paths work under the host sandbox. Without a supported route that preserves mount behavior and the read-only default, a store build is not ready to proceed beyond a prototype.

**What remains reusable?** The sandboxed `MounteeFSKit.appex` has the FSKit module entitlement, receives system-created `FSBlockDeviceResource` values, and contains the filesystem implementation. Apple documents FSKit as compatible with Mac App Store distribution. The C bridge probes volumes read-only and only reopens clean, non-hibernated volumes read/write when its caller requested it. This core is **Likely** reusable with little change, subject to the default-mount safety check below.

**Effort:** A separate Store configuration, public onboarding, signing, and CI path are **M**. Sandboxed device discovery and mounting are **L** because the current implementation has not been tested under App Sandbox and public documentation does not settle those details. Apple entitlement availability and GPL/App Store terms are external gates with unbounded resolution time.

### Finding labels

- **Confirmed:** directly established by repository evidence or explicit current Apple documentation.
- **Likely:** supported by documented platform behavior, but not verified in this app's complete flow.
- **Unknown:** documentation or repository evidence does not decide the behavior; test or Apple/legal confirmation is required.
- **Blocked:** the current implementation violates a documented App Store requirement or relies on unsupported behavior and cannot ship unchanged.

The labels describe confidence/compatibility, not roadmap priority. A public API is not assumed to be sandbox-authorized merely because it exists.

## 3. Critical blockers

### 3.1 Host app is not sandboxed

The main app entitlement file contains only `com.apple.developer.fskit.mount`. Its Xcode Debug/Release configurations use manual Developer ID signing, and the build does not enable App Sandbox. By contrast, the FSKit extension already has `com.apple.security.app-sandbox` and `com.apple.developer.fskit.fsmodule`. Apple requires App Sandbox for any macOS app submitted to the Mac App Store. This is a direct, confirmed build blocker, not a review preference. See [Apple's App Sandbox requirement](https://developer.apple.com/documentation/security/app-sandbox).

The host's `com.apple.developer.fskit.mount` must remain only if the App Store profile and final signature authorize it. The entitlement is present in the Developer ID build, but this repository's profile script queries Developer ID Application certificates and creates `MAC_APP_DIRECT` profiles. No Store profile for these IDs was created during this audit. **Do not infer App Store authorization from the Developer ID build.**

### 3.2 Current FSKit enablement is private and outside the sandbox

`ModuleEnabler.enable()` first calls `FSKitDaemonEnablement.requestEnable()`. That class opens the private Mach service `com.apple.filesystems.fskitd` and guesses two undocumented selectors. If the request fails, `ModuleEnabler` writes `~/Library/Group Containers/group.com.apple.fskit.settings/enabledModules.plist`, then launches `/usr/bin/killall -9 fskit_agent`. These implementation details are acknowledged in source comments. A sandboxed Store app cannot rely on access to that internal group container, and App Review requires public APIs for their documented purposes and forbids access outside the app's designated container.

Apple's public `FSClient.openFileSystemExtensionsSettings()` opens the File System Extensions settings pane. It leaves the enable/disable decision to the user. The local Xcode 27.2 SDK header marks the opener and `mountSingleVolume(...)` as macOS 27 APIs. With the current 26.0 deployment target, show manual Settings instructions on macOS 26 and use the public settings opener on macOS 27. Keep `FSClient.installedExtensions` for state checks. Do not retain the private mechanism in the Store binary, even as a “fallback.” The direct-distribution build can remain isolated and unchanged.

It is **Unknown** whether the module's enabled state survives Mountee updates, removal/reinstall, or switching between App Store and direct builds with the same IDs. Verify each lifecycle on both supported OS versions.

### 3.3 Device discovery and mounting under the host sandbox are not proven

`DiskArbitrationMonitor` registers public Disk Arbitration callbacks, but `refresh()` then lists `/dev`, creates a `DADisk` for each matching `disk*` entry, inspects its description, and reads the kernel mount table. `MountService` invokes public mount/unmount/eject functions; the M4 gate exercises these paths under the current non-sandboxed Developer ID app. That does not establish they succeed in a Mac App Store sandbox.

Apple's archived Disk Arbitration guide says its discussion is primarily for non-sandboxed utilities. Apple's current `FSResource`/`FSBlockDeviceResource` docs describe proxy resources, but a proxy is made from an existing resource object. Apple staff has not answered the broader question of obtaining a block-device resource in a sandboxed GUI app; in the [FSClient mounting discussion](https://developer.apple.com/forums/thread/831391), Apple staff asked the developer to file Feedback so Apple could consider the security consequences. The API documentation and the forum do not establish a replacement for Mountee's manual mount workflow.

**Required gate:** build and sign an App Sandbox test product with the actual Store entitlements, then validate discovery and mount/unmount/eject on macOS 26 and 27. If the supported public path fails on either floor version, do not ship a reduced or privileged workaround as though it preserved functionality. Ask Apple about supported access; otherwise retain direct distribution only or explicitly reconsider the macOS 26 feature floor with the product owner.

### 3.4 The mount default needs an end-to-end safety proof

The menu's “Mount Read-Only” path passes `rdonly`. The C bridge always performs its initial probe read-only and only reopens read/write when requested and the volume is clean and not hibernated. However, the extension interprets a mount request with no `ro`/`rdonly` option as read/write. Its own comments say this is the system default. The app's UI convention alone cannot prove that every path into FSKit originates with a read-only option.

Before release, prove on both OS versions that a fresh/automatic/default mount is read-only and that only an explicit user write action can request read/write. If the system can load the extension without an option, make the extension default read-only and carry an explicit, verifiable write request through the documented mount route. Dirty/hibernated volumes must remain read-only even after the user requests write access. Never introduce a mount route that bypasses the bridge's dirty/hibernation check.

### 3.5 Existing fallback mount path is not a Store route

When Disk Arbitration refuses, `MountService.fallbackMount` creates `~/Library/Mountee/Volumes`, runs `/sbin/mount`, and passes `/dev/<bsdName>`. The Store app must not depend on this path: a child process does not escape its parent sandbox, raw disk access is not implied by the extension's entitlement, and the fixed path is outside the host's sandbox container. Remove the fallback only from the Store product. Keep current behavior in the direct product unless a separate change is approved.

### 3.6 Distribution pipeline and metadata are direct-only

`Mountee.xcodeproj` uses `Developer ID Application` identities and Developer ID profile names for both targets. `scripts/asc-profiles.swift` selects Developer ID certificates and `MAC_APP_DIRECT`; `build-signed.sh` verifies the Developer ID build; `make-installer.sh` requires a Developer ID signature and notarizes/staples a DMG. The release workflow publishes that DMG to GitHub Releases. It has no Store archive/export/upload path. Add a separate Store configuration/workflow; do not convert the current release workflow in place.

Apple says Store submissions do not require notarization because App Store submission performs equivalent security checks. The project settings also do not set `NSHumanReadableCopyright`, which Apple's macOS distribution preparation guidance says to set before upload. Both are actionable release-preparation findings.

## 4. Proposed dual-distribution architecture

Use one Xcode project, one shared filesystem extension, and shared Swift/C implementation. Keep the current app and extension IDs (`app.mountee`, `app.mountee.fskit`) and retain the existing `Mountee` direct-release scheme. Add a Store-specific configuration/scheme and a distinct host entitlement file. The Store host enables App Sandbox and includes `com.apple.developer.fskit.mount` only if Apple authorizes it. The extension stays sandboxed with `com.apple.developer.fskit.fsmodule`.

**Current precedent:** [NTFSTool – NTFS Read & Write](https://apps.apple.com/us/app/ntfstool-ntfs-read-write/id1510209857?mt=12) is a live Mac App Store listing. Its publisher describes a native FSKit extension running in App Sandbox and a System Settings activation step. This demonstrates that a current listing claims to use that product pattern; the listing does not reveal its signed entitlements, prove how its host obtains mount resources, or guarantee review approval for Mountee.

Use build-configuration selection only where behavior truly differs:

- **Direct distribution:** retain the current Developer ID identities/profiles, hardened runtime, notarization, stapling, DMG, and GitHub Release workflow. If its current FSKit activation path remains necessary, keep it out of the Store product and clearly isolate it to the direct product.
- **Mac App Store:** Apple Distribution signing, Mac App Store Connect provisioning profiles for the two explicit IDs, a signed `.xcarchive`, App Store export/upload, App Sandbox for the host, and the public activation UI. Do not notarize or create a DMG for this channel. Require a manual GitHub environment approval before uploading; uploading to App Store Connect must not auto-submit for review or publish.
- **Shared:** same code and tests for `MounteeFSKit`, `bridge/ntfs_bridge.c`, engine, app UI, and versioned FSVolume adapters. Compile private XPC, internal plist, process-kill, and `/sbin/mount` fallback code out of the Store binary and verify absence in the archive. No privileged helper, private API, or disabled security control is part of this design.

The Store build should retain the CLI commands only where they work as ordinary sandboxed app operations. Use the same public operations as the UI; do not grant the CLI a separate path to `/dev`. Keep diagnostic reports in the app container and offer export through a user-selected save panel. `SMAppService.mainApp` login-item registration may be shared, subject to user approval and tests.

Because both channels use the same IDs, they are not independent parallel installations. Test updates and channel switching in both directions and document a supported migration path. Do not create new bundle IDs as an easy workaround: that would change FSKit module identity and break the user's explicit constraint.

## 5. Licensing findings

### Established facts

- The app's `LICENSE` is GPL-3.0.
- `THIRD_PARTY_NOTICES.md` identifies the linked `libntfs-3g.a` as ntfs-3g 2026.9.28 under GPL-2.0-or-later, gives the source tarball SHA-256, and records the readdir patch. `scripts/build-libntfs.sh` builds the static library; the FUSE driver, mount helper, and mtab are disabled. `mkntfs` is test-only and is not shipped.
- Because ntfs-3g is “GPL-2.0 or later,” its authors permit use under GPL-3.0. The notice's statement that it is compatible with this project's GPL-3.0 license is consistent with that license grant.
- Apple's standard App Store EULA includes an exception to its reverse-engineering/derivative-work restriction to the extent permitted by open-source component license terms. App Store Connect also supports a custom EULA. This is relevant evidence, but not a legal opinion that the complete Store terms satisfy every GPL obligation.

### Obligations and unresolved interpretation

The App Store price being zero does not remove copyleft duties. For every Store binary, preserve license texts, copyright/attribution, the exact corresponding source, build scripts, and the applied patch. Tie the source link to the exact released tag/commit and keep it available for that binary; a moving `main` branch is not a durable source reference. Review GPLv3's Corresponding Source and Installation Information requirements for conveyed object code and determine whether App Store delivery, any Apple DRM/receipt controls, and the required end-user terms can all coexist. Do not remove notices or make the source unavailable to simplify submission.

**Classification: Unknown / legal review required.** The documents inspected do not decide whether the combination of GPLv3 obligations and the current Apple Developer Program/App Store terms is acceptable for this particular binary and territory. Have counsel familiar with GPLv3 and Apple distribution terms review the exact Store EULA, Store delivery/installation behavior, source publication plan, and direct-release terms. A different license strategy is not yet established as necessary.

## 9. Open questions

1. **Apple entitlement:** Can Apple issue Mac App Store Connect provisioning profiles for `app.mountee` and `app.mountee.fskit` with the required host `com.apple.developer.fskit.mount` and extension `com.apple.developer.fskit.fsmodule` entitlements for this team?
2. **Sandboxed Disk Arbitration:** On macOS 26 and 27, can this sandboxed host enumerate current and new NTFS disks and complete mount, unmount, eject, and state reporting through the current public APIs? Which of `/dev` listing, `getmntinfo`, and `DADiskCopyDescription` are denied or incomplete?
3. **FSClient mount path:** Can a sandboxed host obtain a documented proxy `FSBlockDeviceResource` for a selected disk and use `mountSingleVolume` on macOS 27? There is no corresponding public method available on macOS 26 in the inspected SDK. Does Disk Arbitration remain the required compatible route on both versions?
4. **Default writability:** Does every system-originated load receive a read-only option unless the user explicitly requests write access? If not, can the extension preserve the required read-only default without an unsupported host API?
5. **Lifecycle:** How do extension registration/enabled state, login item, and app-container data behave through Store update, removal/reinstall, and direct↔Store transitions with the same IDs?
6. **GPL terms:** Does GPLv3's exact Corresponding Source and Installation Information obligation coexist with App Store delivery controls and the selected Store EULA for Mountee's macOS builds? Counsel should answer against the actual Store build and agreement.
7. **Privacy metadata:** What is the accurate privacy declaration after inspecting the exact submitted extension/static dependency, and which privacy-manifest requirements apply to this macOS target and SDK?
8. **Review support:** Can the review team test the extension on its available macOS 26/27 environment, and what non-valuable test volume or hardware must be supplied with the review notes?

## 10. Final recommendation

**Proceed only after resolving specified blockers.** Apple documents FSKit extension distribution through the Mac App Store, and the existing extension and filesystem engine are promising reuse candidates. The current main app is not eligible as configured: it is not sandboxed, it modifies internal FSKit state, and it uses undocumented daemon selectors and a force-restart path. A separate Store build is the smallest architecture that can preserve the direct Developer ID/DMG product while allowing documented activation and Store signing.

Make P0.1 (Store entitlement/profile issuance) and P1.1 (sandboxed disk discovery/mount validation) explicit stop/go gates. Proceed with the Store product only after both succeed and the read-only default is proven. If Apple will not authorize the needed entitlement, or if public sandboxed disk operations cannot preserve required behavior on macOS 26 and 27, keep Mountee direct-distribution only until Apple provides a supported route. Resolve GPL terms with counsel before submission; the current materials do not justify either declaring an automatic GPL blocker or claiming legal clearance.

**Not checked:** no App Store profile, sandboxed archive, physical drive, or exact privacy/EULA submission was validated. **Key risks:** host disk permissions, `fskit.mount` profile eligibility, default mount writability, and GPL/App Store terms remain unproven.
